## 2. 官方计费规则深度分析

### 2.1 在线推理（常规）价格表

| 输入长度条件 | 输入(非音频)<br>元/百万token | 输入(音频)<br>元/百万token | 缓存存储<br>元/百万token/小时 | 缓存命中(非音频)<br>元/百万token | 缓存命中(音频)<br>元/百万token | 输出<br>元/百万token |
|---|---|---|---|---|---|---|
| [0, 32] | 0.6 | 9.0 | 0.017 | 0.12 | 1.8 | 3.6 |
| (32, 128] | 0.9 | 13.5 | 0.017 | 0.18 | 2.7 | 5.4 |
| (128, 256] | 1.8 | 27.0 | 0.017 | 0.36 | 5.4 | 10.8 |

### 2.2 在线推理（低延迟）价格表

| 输入长度条件 | 输入(非音频)<br>元/百万token | 输入(音频)<br>元/百万token | 缓存命中(非音频)<br>元/百万token | 缓存命中(音频)<br>元/百万token | 输出<br>元/百万token |
|---|---|---|---|---|---|
| [0, 32] | 1.2 | 18.0 | 0.24 | 3.6 | 7.2 |
| (32, 128] | 1.8 | 27.0 | 0.36 | 5.4 | 10.8 |
| (128, 256] | 3.6 | 54.0 | 0.72 | 10.8 | 21.6 |

> **关键观察**：低延迟档价格为常规档的 **2 倍**。

### 2.3 官方计费公式

```
在线推理费用 = 输入(非音频)单价 × 输入(非音频)token
            + 输入(音频)单价 × 输入(音频)token
            + 缓存命中(非音频)单价 × 缓存命中(非音频)token
            + 缓存命中(音频)单价 × 缓存命中(音频)token
            + 缓存存储单价 × 缓存存储token × 时长(小时)
            + 输出单价 × 输出token
```

### 2.4 6 个计费维度识别

| # | 维度 | 单位 | 计费触发条件 |
|---|------|------|------------|
| 1 | 输入(非音频) | 元/百万token | 必发生 |
| 2 | 输入(音频) | 元/百万token | 请求含音频输入 |
| 3 | 缓存命中(非音频) | 元/百万token | 启用上下文缓存且命中 |
| 4 | 缓存命中(音频) | 元/百万token | 启用上下文缓存且音频部分命中 |
| 5 | 缓存存储 | 元/百万token/小时 | 启用上下文缓存功能 |
| 6 | 输出 | 元/百万token | 必发生 |

外加：**分段计费**机制，按输入长度 `[0,32]/(32,128]/(128,256]` 区分 3 档单价。

## 3. 项目计费能力 vs 官方需求 对照

### 3.1 billingexpr 表达式系统能力

参考项目 [`pkg/billingexpr/expr.md`](file:///Users/cheng/workspace/project/TengYou/newapi/new-api/pkg/billingexpr/expr.md) 与 [`pkg/billingexpr/types.go`](file:///Users/cheng/workspace/project/TengYou/newapi/new-api/pkg/billingexpr/types.go)，当前系统支持的变量：

| 变量 | 含义 |
|------|------|
| `p` | 输入 token 数（自动排除子类别） |
| `c` | 输出 token 数（自动排除子类别） |
| `len` | 输入上下文总长度（**用于阶梯条件**） |
| `cr` | 缓存命中(读取) token 数 |
| `cc` / `cc1h` | 缓存创建 token (Claude 5min/1h TTL) |
| `img` / `img_o` | 图片输入/输出 token |
| `ai` / `ao` | 音频输入/输出 token |

**关键能力**：
- 阶梯条件：`len <= 32 ? tier(...) : len <= 128 ? tier(...) : tier(...)`
- 多模态分离计价：`p + ai + img + ao` 各自独立单价
- 缓存命中独立计价：`cr`
- 系数单位为 $/1M tokens（详见 [`settle.go`](file:///Users/cheng/workspace/project/TengYou/newapi/new-api/pkg/billingexpr/settle.go)）

### 3.2 6 维度支持情况

| # | 官方维度 | 项目变量 | 支持状态 | 说明 |
|---|---------|---------|---------|------|
| 1 | 输入(非音频) | `p` | 完全支持 | 直接 `p * 单价` |
| 2 | 输入(音频) | `ai` | 完全支持 | 直接 `ai * 单价` |
| 3 | 缓存命中(非音频) | `cr` | 完全支持 | 直接 `cr * 单价` |
| 4 | 缓存命中(音频) | 无 | 合并计费 | 见 4.1 |
| 5 | 缓存存储(token×小时) | 无 | 无法支持 | 见 4.2 |
| 6 | 输出 | `c` | 完全支持 | 直接 `c * 单价` |
| - | 分段计费 | `len` 条件 | 完全支持 | 三元运算符嵌套 |

**结论：6 个核心维度中 4 个完全支持，1 个合并计费（影响极小），1 个无法支持（与 API 调用本身分离）。**

## 4. 无法 100% 精确支持的细节说明

### 4.1 缓存命中(音频) — 合并计费

**原因**：火山引擎 OpenAI 兼容 API 响应中 `prompt_tokens_details.cached_tokens` 字段是一个**总数**，并不区分音频/非音频。火山引擎实际计费时大概率也是合并计算（按非音频单价）。

**项目当前行为**：使用 `cr` 变量读取 `cached_tokens` 总数，按"缓存命中(非音频)"单价计费。

**影响评估**：极小。豆包模型 API 响应中 `cached_tokens` 通常是文本缓存命中为主，音频缓存命中场景非常罕见。

**建议**：使用 `cr * 缓存命中(非音频)单价` 即可，与火山引擎实际计费行为一致。

### 4.2 缓存存储费用 — 无法支持

**原因**：这是火山引擎"上下文缓存"功能的额外存储费用（按 `token × 小时` 计费）。但火山引擎 OpenAI 兼容 API 响应中**并不暴露**"缓存存储 token 数"和"存储时长"字段，因此即便修改代码也无法获取此数据。

**计费特征**：该费用通常由火山引擎直接计入账户账单，与单次 API 调用本身分离。即每次 API 调用不会立即产生此费用，而是后台按存储时长累计计费。

**影响评估**：
- 如果用户**不主动开启**火山引擎"上下文缓存"功能 → 此费用不产生，无影响
- 如果用户**开启**该功能 → 此费用在火山引擎账户账单中体现，但无法通过本项目转嫁给终端用户

**建议**：在本项目层面忽略此费用（属于渠道侧成本，不影响终端用户单次调用计费）。如需精确转嫁，建议在渠道侧通过 group_ratio 整体调整。

## 5. 前端配置详细指引（常规推理）

### 5.1 前置确认：USD2RMB 汇率设置

billingexpr 表达式系数单位为 **$/1M tokens**。系数换算取决于系统设置 `Price`（即 `operation_setting.Price`，前端可配置）。

**查看路径**：控制台 → 系统设置 → 通用设置 → 价格（Price）

**两种情况**：

| Price 设置 | 含义 | 系数换算公式 |
|-----------|------|------------|
| `1`（按用户 profile，统一 RMB 结算） | 1 元 = $1 | 系数 = 官方元价 |
| `7.3`（默认值） | 7.3 元 = $1 | 系数 = 官方元价 / 7.3 |

> 下文示例按 `Price=1` 给出（与用户 profile 一致）。若 `Price=7.3`，将每个系数除以 7.3 即可。

### 5.2 配置步骤

#### 步骤 1：进入控制台模型管理

访问：`控制台 → 模型管理`，点击「新建模型」。

#### 步骤 2：填写基础信息

| 字段 | 值 |
|------|---|
| Model Name | `doubao-seed-2.0-lite` |
| Description | `豆包 Seed 2.0 Lite 多模态大模型，支持文本/音频输入，按输入长度分段计费` |
| Icon | `VolcEngine`（或 `Doubao`） |
| Vendor | VolcEngine（火山引擎） |
| Tags | `["chat", "multimodal", "audio"]` |
| Name Rule | `Exact Match`（精确匹配） |
| Status | 启用 |

#### 步骤 3：配置端点

```json
{
  "openai": {
    "path": "/v1/chat/completions",
    "method": "POST"
  }
}
```

> 豆包模型通过火山引擎 OpenAI 兼容接口调用，端点路径为 `/api/v3/chat/completions`（由 [`volcengine/adaptor.go`](file:///Users/cheng/workspace/project/TengYou/newapi/new-api/relay/channel/volcengine/adaptor.go) 自动拼接，前端配置 `/v1/chat/completions` 即可）。

#### 步骤 4：配置价格（关键步骤）

##### 方式 A：分层计费表达式（推荐，完全兼容官方分段计费）

1. 进入：`控制台 → 系统设置 → 模型倍率设置 → 分层计费编辑器`
2. 找到 `doubao-seed-2.0-lite`，切换到「原始模式（Raw mode）」
3. 粘贴以下表达式（按 `Price=1`，元价即系数）：

```
len <= 32
  ? tier("tier1", p * 0.6 + ai * 9.0 + cr * 0.12 + c * 3.6)
  : len <= 128
    ? tier("tier2", p * 0.9 + ai * 13.5 + cr * 0.18 + c * 5.4)
    : tier("tier3", p * 1.8 + ai * 27.0 + cr * 0.36 + c * 10.8)
```

**表达式说明**：

| 段 | 条件 | p 系数 | ai 系数 | cr 系数 | c 系数 |
|----|------|-------|--------|--------|-------|
| tier1 | len ≤ 32 | 0.6 | 9.0 | 0.12 | 3.6 |
| tier2 | 32 < len ≤ 128 | 0.9 | 13.5 | 0.18 | 5.4 |
| tier3 | len > 128 | 1.8 | 27.0 | 0.36 | 10.8 |

> 如果系统 `Price=7.3`，把每个系数除以 7.3：
> ```
> len <= 32
>   ? tier("tier1", p * 0.0822 + ai * 1.2329 + cr * 0.0164 + c * 0.4932)
>   : len <= 128
>     ? tier("tier2", p * 0.1233 + ai * 1.8493 + cr * 0.0247 + c * 0.7397)
>     : tier("tier3", p * 0.2466 + ai * 3.6986 + cr * 0.0493 + c * 1.4795)
> ```

4. 保存。系统会自动进行 SmokeTest 验证表达式语法。

##### 方式 B：传统倍率配置（简化版，不分段）

如果不需要分段计费，可使用传统倍率配置。在模型编辑抽屉中：

| 字段 | 值（Price=1 时） | 值（Price=7.3 时） |
|------|----------------|------------------|
| Pricing mode | per-token | per-token |
| Input mode | price | price |
| Prompt price (USD/1M) | `0.6` | `0.0822` |
| Completion price | `3.6` | `0.4932` |
| 高级选项 → Cache ratio | `0.2` (= 0.12/0.6) | `0.2` |
| 高级选项 → Audio ratio | `15` (= 9.0/0.6) | `15` |

**换算公式**：
- `ModelRatio = Prompt price / 2`（项目内部约定：1 倍率 = $2/1M tokens）
- `CompletionRatio = Completion price / Prompt price`
- `CacheRatio = 缓存命中价 / 输入价`
- `AudioRatio = 音频输入价 / 输入价`

#### 步骤 5：配置渠道

1. 进入：`控制台 → 渠道管理`
2. 新建渠道：
   - 类型：`VolcEngine`
   - Base URL：`https://ark.cn-beijing.volces.com`
   - API Key：火山引擎 ARK API Key
   - 模型：`doubao-seed-2.0-lite`
3. 保存并测试。

## 6. 计费验证示例

### 6.1 场景：纯文本输入 + 输出

**请求**：1M 文本输入 + 0.5M 输出，无音频，无缓存命中

**官方扣费**（按 tier1，len ≤ 32）：
- 输入：1,000,000 × 0.6 / 1,000,000 = 0.6 元
- 输出：500,000 × 3.6 / 1,000,000 = 1.8 元
- 合计：**2.4 元**

**项目扣费**（表达式 `p * 0.6 + ai * 9.0 + cr * 0.12 + c * 3.6`）：
- exprOutput = 1,000,000 × 0.6 + 0 × 9.0 + 0 × 0.12 + 500,000 × 3.6 = 2,400,000
- quota = 2,400,000 / 1,000,000 × 500,000 × 1 (groupRatio) = 1,200,000
- USD = 1,200,000 / 500,000 = $2.4 = **2.4 元**（Price=1）

✅ 完全一致。

### 6.2 场景：多模态输入（文本 + 音频）

**请求**：0.8M 文本 + 0.2M 音频输入 + 0.5M 输出

**官方扣费**（tier1）：
- 文本输入：0.8M × 0.6 = 0.48 元
- 音频输入：0.2M × 9.0 = 1.8 元
- 输出：0.5M × 3.6 = 1.8 元
- 合计：**4.08 元**

**项目扣费**：
- exprOutput = 800,000 × 0.6 + 200,000 × 9.0 + 0 × 0.12 + 500,000 × 3.6 = 4,080,000
- quota = 4,080,000 / 1,000,000 × 500,000 = 2,040,000
- USD = $4.08 = **4.08 元** ✅

### 6.3 场景：分段计费（输入 > 128K）

**请求**：200K 文本输入 + 14K 输出（len=200K，命中 tier3）

**官方扣费**：
- 输入：0.2M × 1.8 = 0.36 元
- 输出：0.014M × 10.8 = 0.1512 元
- 合计：**0.5112 元**

**项目扣费**（tier3 表达式：`p * 1.8 + ai * 27.0 + cr * 0.36 + c * 10.8`）：
- exprOutput = 200,000 × 1.8 + 14,000 × 10.8 = 511,200
- quota = 511,200 / 1,000,000 × 500,000 = 255,600
- USD = $0.5112 = **0.5112 元** ✅

## 7. 常规 vs 低延迟计费区分方案

### 7.1 问题背景

火山引擎对同一个 `doubao-seed-2.0-lite` 模型提供两种推理服务：

| 服务类型 | 特点 | 价格倍数 |
|---------|------|---------|
| 在线推理（常规） | 标准 TPM、标准延迟 | 1x |
| 在线推理（低延迟） | 更高并发、更低延迟 | **2x**（所有维度翻倍） |

**关键约束**：常规/低延迟由**火山引擎接入点（Endpoint）**决定，而非请求参数。也就是说，API Key + Endpoint ID 决定了本次调用走常规还是低延迟计费。

### 7.2 方案对比

| 方案 | 实现方式 | 优点 | 缺点 | 推荐度 |
|------|---------|------|------|-------|
| A. 双模型名 + 双渠道 | 客户端用不同模型名触发不同计费 | 干净、清晰、零代码改动 | 需创建两个模型元数据 | ⭐⭐⭐⭐⭐ |
| B. billingexpr 请求规则 | 通过 header 区分 | 单模型统一管理 | 客户端需带特殊 header，且与火山引擎实际计费机制不符 | ❌ 不可行 |
| C. 用户分组倍率 | 不同分组不同倍率 | 简单 | 粒度太粗，影响所有模型 | ❌ 不推荐 |

### 7.3 推荐方案：双模型名 + 双渠道 + 模型重定向

#### 7.3.1 方案架构

```
┌─────────────────────────────────────────────────────────────┐
│                     客户端请求                                │
│  ┌──────────────────────┐  ┌──────────────────────────────┐ │
│  │ model: doubao-seed-  │  │ model: doubao-seed-2.0-lite- │ │
│  │ 2.0-lite             │  │ fast                         │ │
│  │ (常规)                │  │ (低延迟)                      │ │
│  └──────────┬───────────┘  └───────────┬──────────────────┘ │
└─────────────┼──────────────────────────┼─────────────────────┘
              │                          │
              ▼                          ▼
   ┌─────────────────────┐    ┌─────────────────────────┐
   │  渠道 A（常规）       │    │  渠道 B（低延迟）         │
   │  - API Key: 常规接入点 │    │  - API Key: 低延迟接入点  │
   │  - 模型重定向：       │    │  - 模型重定向：           │
   │    doubao-seed-2.0-  │    │    doubao-seed-2.0-lite- │
   │    lite → ep-常规xxx │    │    fast → ep-低延迟xxx   │
   └──────────┬──────────┘    └───────────┬─────────────┘
              │                           │
              ▼                           ▼
   ┌─────────────────────────────────────────────────┐
   │         火山引擎上游 API                         │
   │  - 接入点 A：常规推理，按常规价计费              │
   │  - 接入点 B：低延迟推理，按低延迟价计费          │
   └─────────────────────────────────────────────────┘
              │                           │
              ▼                           ▼
   ┌─────────────────────┐    ┌─────────────────────────┐
   │  分层计费表达式 A    │    │  分层计费表达式 B        │
   │  （常规价格系数）    │    │  （低延迟价格系数=2x）   │
   │  命中 tier1/2/3     │    │  命中 tier1/2/3         │
   └─────────────────────┘    └─────────────────────────┘
```

#### 7.3.2 配置步骤

##### 步骤 1：在火山引擎控制台创建两个接入点

1. 登录火山引擎控制台 → 火山方舟 → 在线推理 → 接入点管理
2. 为 `doubao-seed-2.0-lite` 模型创建两个接入点：
   - 接入点 A：选择「在线推理（常规）」→ 获得 Endpoint ID（如 `ep-2026xxxxxx-xxxxx`）
   - 接入点 B：选择「在线推理（低延迟）」→ 获得 Endpoint ID（如 `ep-2026yyyyyy-yyyyy`）
3. 分别为两个接入点创建 API Key（或共用同一 API Key）。

##### 步骤 2：在 newapi 创建两个模型元数据

**模型 A（常规）**：

| 字段 | 值 |
|------|---|
| Model Name | `doubao-seed-2.0-lite` |
| Description | `豆包 Seed 2.0 Lite 多模态大模型（常规推理）` |
| Tags | `["chat", "multimodal", "audio", "standard"]` |

**模型 B（低延迟）**：

> 命名约定建议：`-fast` 后缀表示低延迟版本，直观且符合 OpenAI 生态惯例（如 `gpt-4o-mini` → `gpt-4o`）。

##### 步骤 3：为两个模型分别配置分层计费表达式

**模型 A（常规）表达式**（同第 5.2 节步骤 4 方式 A）：

```
len <= 32
  ? tier("tier1", p * 0.6 + ai * 9.0 + cr * 0.12 + c * 3.6)
  : len <= 128
    ? tier("tier2", p * 0.9 + ai * 13.5 + cr * 0.18 + c * 5.4)
    : tier("tier3", p * 1.8 + ai * 27.0 + cr * 0.36 + c * 10.8)
```

**模型 B（低延迟）表达式**（所有系数 × 2）：

```
len <= 32
  ? tier("tier1", p * 1.2 + ai * 18.0 + cr * 0.24 + c * 7.2)
  : len <= 128
    ? tier("tier2", p * 1.8 + ai * 27.0 + cr * 0.36 + c * 10.8)
    : tier("tier3", p * 3.6 + ai * 54.0 + cr * 0.72 + c * 21.6)
```

**两份表达式系数对照表**：

| 段 | 条件 | 维度 | 常规系数 | 低延迟系数 |
|----|------|------|---------|----------|
| tier1 | len ≤ 32 | p | 0.6 | 1.2 |
| tier1 | len ≤ 32 | ai | 9.0 | 18.0 |
| tier1 | len ≤ 32 | cr | 0.12 | 0.24 |
| tier1 | len ≤ 32 | c | 3.6 | 7.2 |
| tier2 | 32 < len ≤ 128 | p | 0.9 | 1.8 |
| tier2 | 32 < len ≤ 128 | ai | 13.5 | 27.0 |
| tier2 | 32 < len ≤ 128 | cr | 0.18 | 0.36 |
| tier2 | 32 < len ≤ 128 | c | 5.4 | 10.8 |
| tier3 | len > 128 | p | 1.8 | 3.6 |
| tier3 | len > 128 | ai | 27.0 | 54.0 |
| tier3 | len > 128 | cr | 0.36 | 0.72 |
| tier3 | len > 128 | c | 10.8 | 21.6 |

> 以上系数按 `Price=1` 给出。若 `Price=7.3`，将所有系数除以 7.3。

## 8. 影响范围与副作用审视

### 8.1 不修改代码的影响

零代码改动意味着：
- 不影响其他模型计费逻辑
- 不影响数据库结构
- 不影响 API 接口
- 不影响前端构建
- 无回归风险

### 8.2 配置后的影响范围

| 影响项 | 范围 |
|-------|------|
| 模型广场展示 | 显示 doubao-seed-2.0-lite（+ fast）卡片，带「动态定价」徽章 |
| 模型详情抽屉 | 显示 3 档分段价格表 |
| 调用计费 | 按 billingexpr 表达式实时计算扣费 |
| 日志展示 | 日志详情显示匹配的 tier（tier1/tier2/tier3）和表达式 |
| 渠道转发 | 通过火山引擎适配器转发到 `/api/v3/chat/completions` |

### 8.3 注意事项

1. **API Key 权限**：火山引擎 API Key 需在火山引擎控制台开通 doubao-seed-2.0-lite 模型权限。
2. **上下文缓存功能**：若需启用火山引擎"上下文缓存"功能以享受缓存命中优惠价，需在火山引擎控制台单独开启，本项目自动通过 `cached_tokens` 字段读取命中数。
3. **音频输入支持**：豆包模型的音频输入需要通过 OpenAI 多模态消息格式（`input_audio` content type）传递，本项目已原生支持。
4. **低延迟接入点开通**：低延迟推理需在火山引擎控制台单独开通「TPM 保障包」或「低延迟」服务，否则接入点创建时无法选择低延迟选项。
5. **模型重定向 Endpoint ID**：火山引擎 API 调用时 `model` 参数需传 Endpoint ID（如 `ep-xxxxx`），不是模型名。务必在渠道的模型重定向中配置正确映射。

## 9. 总结

| 项目 | 结论 |
|-----|------|
| 是否需要修改代码 | **不需要** |
| 是否完全兼容官方计费 | **95% 兼容**（4/6 维度完全支持，1 个合并计费，1 个无法支持） |

**最终建议**：直接按第 5 节和第 7 节指引在前端配置分层计费表达式与双渠道即可。无需修改任何代码。
